  <Accordion title="Parse PRD">
    ```bash
    # Parse a PRD file and generate tasks
    taskgraph parse-prd <prd-file.txt>

    # Limit the number of tasks generated
    taskgraph parse-prd <prd-file.txt> --num-tasks=10

    # Replace the current tag's tasks, or add to them
    taskgraph parse-prd <prd-file.txt> --force
    taskgraph parse-prd <prd-file.txt> --append

    # Ask about gaps in the PRD first, and save the answers in it
    taskgraph parse-prd <prd-file.txt> --clarify
    taskgraph parse-prd <prd-file.txt> --clarify --yes

    # For agents: print the questions as JSON, then pass the answers back
    taskgraph parse-prd <prd-file.txt> --clarify --json > questions.json
    taskgraph parse-prd <prd-file.txt> --answers questions.json
    ```

    In a terminal, each task is printed as soon as Claude finishes writing it, with an elapsed-time counter. `--force` numbers the new tasks from 1; `--append` continues after the highest existing ID. With `--append`, Claude sees the existing tasks' IDs and titles, so a new task can depend on one of them. The new tasks are added to the tag as it is when they are saved: a change another command or agent made to the tag while Claude was working is kept, and the new tasks take the next free IDs after it.

    Each task records the PRD section it came from in `metadata.source`, such as `docs/prd.md#authentication`, and `taskgraph show` prints it.

    Re-running `--append` on a PRD you edited sends Claude only the sections added since the last parse, so existing tasks aren't duplicated. Sections whose text changed and sections you removed are listed with the tasks that came from them; those tasks are left as they are for you to review. An unchanged PRD makes no AI call and adds no tasks:

    ```
    1 new section in docs/prd.md · #export
    ⚠ 1 changed section · #notes · may be stale: task 2
    ⚠ 1 removed section · #sharing · task 3 cites it
    ```

    Each change is reported once: after the run, the edited PRD is the new baseline. With `--append`, Claude decides how many tasks the new sections need; `--num-tasks` applies to whole-PRD parses.

    `--clarify` asks up to 5 questions about requirements the PRD leaves open (the data store, sign-in, platforms, scope), each with a suggested answer. Press Enter to keep the suggestion. The answers are saved in the PRD under `## Clarifications`, then the tasks are generated from it, so the decisions stay in the repo:

    ```markdown
    ## Clarifications

    - **Q:** Which database should the app use?
      **A:** PostgreSQL 16
    ```

    Running it again skips questions the section already answers, and a new answer to the same question replaces the old one. With no terminal to ask in, or with `--yes`, the suggested answers are used. If there is nothing to ask, it goes straight to the tasks. Ctrl-C leaves the PRD unchanged.

    `--clarify --json` prints only `{"prd", "questions": [{"question", "suggestedAnswer"}]}` and changes nothing. Add an `"answer"` to each question and pass the file to `--answers` (or `-` for stdin); a question without an `"answer"` keeps its suggestion. `--answers` saves the answers and generates the tasks without asking the model for questions again.

    Each task comes with 2-5 acceptance criteria taken from the PRD, all unchecked. `taskgraph show <id>` numbers them, and `set-status done` waits until they are checked off (see Set Status).
  </Accordion>

  <Accordion title="List Tasks">
    ```bash
    # List all tasks
    taskgraph list

    # List tasks with a specific status
    taskgraph list --status=<status>

    # List tasks with subtasks
    taskgraph list --with-subtasks

    # List tasks with a specific status and include subtasks
    taskgraph list --status=<status> --with-subtasks

    # Watch for changes and auto-refresh
    taskgraph list --watch
    taskgraph list -w

    # Compact output format
    taskgraph list --compact
    taskgraph list -c

    # Watch mode with compact output
    taskgraph list -w -c

    # Hide the header
    taskgraph list --no-header
    ```
  </Accordion>

  <Accordion title="Show Next Task">
    ```bash
    # Show the next task to work on: dependencies done, then priority,
    # then most unblocked work, then fewer dependencies, then lowest ID
    taskgraph next

    # Take the next task nobody has started: set it in-progress and record
    # who claimed it (session ID, else your user name) in one locked write,
    # so two sessions never get the same task. Setting it back to pending
    # releases it.
    taskgraph next --claim
    ```
  </Accordion>

  <Accordion title="Show the Dependency Tree">
    ```bash
    # Draw all tasks as a tree: each task sits under the dependency it waits on
    # longest, other dependencies are listed after its title, and the next
    # task is marked "← next". Loops and missing dependency IDs are called out.
    taskgraph graph

    # Only one task and the tasks drawn under it
    taskgraph graph --id=3

    # Machine-readable tree, with bottlenecks, criticalPath and per-node
    # `inferred` dependencies
    taskgraph graph --format json
    ```

    Text output also marks bottlenecks (`blocks N`), the critical path (`◆`)
    and AI-inferred dependencies (`*`), with a legend. See
    [Dependency Graph](/capabilities/dependency-graph).
  </Accordion>

  <Accordion title="Explain Why a Task Is Blocked">
    ```bash
    # Follow a task's unfinished dependencies down to the root causes: work
    # that is ready to start, deferred or blocked tasks, dependency IDs that
    # match no task, and dependency loops (including a task that lists itself).
    # Each root cause comes with the command that fixes it.
    taskgraph why <id>
    # or
    taskgraph why --id=<id>

    # Subtasks work too
    taskgraph why 3.2

    # Machine-readable explanation
    taskgraph why <id> --format json
    ```

    The JSON has the task's `id`, `title`, `status`, `blocked`, the `tag`, a
    nested `blockers` tree (each node has `id`, `title`, `status`, `blockers`,
    and `kind` where a chain ends: `ready`, `stalled`, `missing` or `cycle`;
    a task already shown elsewhere is marked `repeated`), and `rootCauses`.
    A `missing` root cause lists the tasks that name it in `listedBy`; a
    `cycle` root cause lists its members in `cycle` and the dependencies to
    remove in `edges` (`from` depends on `to`).
  </Accordion>

  <Accordion title="Prime a Coding Agent">
    ```bash
    # Print what an agent needs at the start of a session: the tag, the task
    # in progress with how to tell it's done (acceptance criteria, else test
    # strategy), the next three ready tasks in `next` order, and the five
    # workflow rules, with free text in single quotes. Under 40 lines, 80
    # columns wide when piped.
    taskgraph prime

    # Another tag, or the same context as JSON
    taskgraph prime --tag=feature-auth
    taskgraph prime --json

    # Only the in-progress tasks with no note since a time (ISO); prints
    # nothing when every one has a note. The plugin's Stop hook uses it.
    taskgraph prime --unnoted-since=2026-10-23T09:00:00Z
    ```

    `prime` is for agents, so `taskgraph --help` mentions it under its groups
    rather than in them. The Claude Code plugin runs it from a SessionStart
    hook, at startup and again after the conversation is compacted, so Claude
    doesn't start cold. The hook prints nothing in a folder without
    `.taskgraph/`.

    The JSON has `tag`, `counts` (`total`, `done`), `inProgress` (each with
    `id`, `title`, `status`, `priority`, `doneWhen`, and `parentTitle` for a
    subtask), `ready` (the same fields without `doneWhen`) and `rules`
    (`text` and `command`). With `--unnoted-since`, the JSON is
    `{ "unnoted": [...] }` with the `ready` fields for each task.

    A note counts if a `taskgraph note`, `update-subtask` or `research --save`
    block was added to the task (or its parent or subtask) at or after that
    time.
  </Accordion>

  <Accordion title="Log a Progress Note">
    ```bash
    # Append a note to a task or subtask, exactly as written, with a timestamp.
    # No AI call, so it takes well under a second.
    taskgraph note 3 "Chose argon2 over bcrypt: the login API already uses it"
    taskgraph note 3.2 "Cookie path was wrong; fixed in auth/session.ts"

    # A longer note from a file, or from stdin with -
    taskgraph note 3 --file notes.md
    git log -1 --format=%B | taskgraph note 3 --file -
    ```

    Prints one line, `✓ Added a note to task 3  <title>`. The note goes at the
    end of the task's details in an `<info added on <time>>` block, the same
    block `update-subtask` writes, and nothing else in `tasks.json` changes.
    `<time>` is an ISO 8601 UTC timestamp such as `2026-10-23T14:02:11.000Z`,
    repeated in the closing `</info added on <time>>` line. A note can be at
    most 64 KB.
    MCP clients use the `add_note` tool. Use `update-subtask` or
    `update-task --append` when you want the AI to write the note instead.
  </Accordion>

  <Accordion title="Update a Subtask">
    ```bash
    # Append additional information to a specific subtask
    taskgraph update-subtask --id=<parentId.subtaskId> --prompt='<prompt>'

    # Example: Add details about API rate limiting to subtask 2 of task 5
    taskgraph update-subtask --id=5.2 --prompt="Add rate limiting of 100 requests per minute"

    # Use research-backed updates (research model)
    taskgraph update-subtask --id=<parentId.subtaskId> --prompt='<prompt>' --research
    ```

    Unlike the `update-task` command which replaces task information, the `update-subtask` command _appends_ new information to the existing subtask details, marking it with a timestamp. The AI writes the appended text from your prompt; to save a note exactly as written, use `taskgraph note`.
  </Accordion>

  <Accordion title="Set Task Status">
    ```bash
    # Set status of a single task
    taskgraph set-status --id=<id> --status=<status>

    # Set status for multiple tasks
    taskgraph set-status --id=1,2,3 --status=<status>

    # Set status for subtasks
    taskgraph set-status --id=1.1,1.2 --status=<status>

    # Check off acceptance criteria by the numbers `show` lists
    taskgraph set-status 3 --check 1,2

    # Check the last ones and mark the task done in one step
    taskgraph set-status 3 done --check 3

    # Clear a criterion checked by mistake
    taskgraph set-status 3 --uncheck 2
    ```

    A task with acceptance criteria, or a project with a [Definition of Done](/configuration#definition-of-done), can't be marked done while any item is unchecked. `set-status` lists the unchecked items and the `--check` command that clears them. `--force` marks the task done anyway. A subtask is gated by its own criteria only, and a parent whose last subtask finishes stays in progress until its own items are checked.

    In Claude Code, the plugin's `/taskgraph:to-done <id>` does the checking for you: the `task-checker` agent compares your changes with each numbered item, the ones it can show evidence for are checked, and the rest are reported to you. It then saves a three-line summary on the task (what changed, files, follow-ups) and marks it done. It never passes `--force` unless you ask.

    When marking a task as "done", all of its subtasks will automatically be marked as "done" as well.
  </Accordion>

  <Accordion title="Expand Tasks">
    ```bash
    # Expand a specific task with subtasks
    taskgraph expand --id=<id> --num=<number>

    # Expand with additional context
    taskgraph expand --id=<id> --prompt='<context>'

    # Expand all pending tasks
    taskgraph expand --all

    # Force regeneration of subtasks for tasks that already have them
    taskgraph expand --all --force

    # Research-backed subtask generation for a specific task
    taskgraph expand --id=<id> --research

    # Research-backed generation for all tasks
    taskgraph expand --all --research
    ```

    Each new subtask gets 2-5 acceptance criteria of its own, unchecked. A subtask can't be marked done until they are checked off with `taskgraph set-status <id> --check <n>`.

    `--force` replaces a task's subtasks. Dependencies and `related` / `discovered-from` links on the old subtasks are dropped first, so they don't end up naming the new subtasks that reuse their IDs.
  </Accordion>

  <Accordion title="Clear Subtasks">
    ```bash
    # Clear subtasks from a specific task
    taskgraph clear-subtasks --id=<id>

    # Clear subtasks from multiple tasks
    taskgraph clear-subtasks --id=1,2,3

    # Clear subtasks from all tasks
    taskgraph clear-subtasks --all
    ```

    Dependencies on the cleared subtasks, and `related` / `discovered-from` links to them, are dropped too, as `remove-task` and `remove-subtask` do.
  </Accordion>

  <Accordion title="Managing Task Dependencies">
    ```bash
    # Add a dependency to a task
    taskgraph add-dependency --id=<id> --depends-on=<id>

    # Link two tasks without making one wait for the other
    taskgraph add-dependency --id=<id> --depends-on=<id> --type=related

    # Remove a dependency (or a related / discovered-from link) from a task
    taskgraph remove-dependency --id=<id> --depends-on=<id>

    # Validate dependencies without fixing them
    taskgraph validate-dependencies

    # Find and fix invalid dependencies automatically
    taskgraph fix-dependencies
    ```

    Once `parse-prd` has recorded where tasks came from, `validate-dependencies` also checks the PRD: it lists sections no task covers, tasks that cite a heading the PRD no longer has (renamed or removed), and tasks with no section. A task covers its section and the sections inside it. These are warnings: only dependency problems make the command exit 1.

    ```
    ✓ No dependency problems · 6 tasks, 4 dependencies
    ⚠ 2 of 10 PRD sections have no task · docs/prd.md
      #search--tags   Search & Tags
      #rate-limiting  Rate limiting
    ⚠ 1 task cites a heading docs/prd.md no longer has
      3  #password-reset
    ```
  </Accordion>

  <Accordion title="Add a New Task">
    ```bash
    # Add a new task using AI
    taskgraph add-task --prompt="Description of the new task"

    # Add a task with dependencies
    taskgraph add-task --prompt="Description" --dependencies=1,2,3

    # Add a task with priority
    taskgraph add-task --prompt="Description" --priority=high

    # File work you found while doing task 3; it doesn't wait for task 3
    taskgraph add-task --prompt="Description" --discovered-from=3

    # Add acceptance criteria (repeat --ac for each one)
    taskgraph add-task --prompt="Description" --ac="Users can log in" --ac="Tokens expire after 15 minutes"
    ```

  <Accordion title="Initialize a Project">
    ```bash
    # Initialize a new project with TaskGraph structure
    taskgraph init

    # Import a Task Master project (.taskmaster/) into .taskgraph/
    taskgraph init --from-taskmaster

    # Skip the Claude Code integration (CLAUDE.md import)
    taskgraph init --no-claude

    # Also register the MCP server in the project's .mcp.json
    taskgraph init --mcp

    # Only set up Git to merge tasks.json and archive.json by task
    # (existing projects; once per clone, and again after upgrading)
    taskgraph init --merge-driver
    ```

    `init` sets up the Claude Code integration by default: it copies TaskGraph's agent guide to `.taskgraph/CLAUDE.md` and imports it from your `CLAUDE.md`. Interactive runs ask, with Yes as the default; `--yes` sets it up without asking, and `--no-claude` skips it. Slash commands and session hooks come from the plugin.

    `init` writes no `.mcp.json` unless you pass `--mcp`, because the CLI and the plugin need no MCP server. `--mcp` needs the Claude Code integration, so it can't be combined with `--no-claude`. `--rules claude` still works; `claude` is the only rule profile.

    Inside a Git repository, `init` also sets up the [tasks.json merge driver](/capabilities/merge-driver), so two branches that both add or archive tasks merge without an ID clash.
  </Accordion>

  <Accordion title="Move Tasks">
    ```bash
    # Move a task or subtask to a new position
    taskgraph move --from=<id> --to=<id>

    # Move task to become a subtask
    taskgraph move --from=5 --to=7

    # Move subtask to become a standalone task
    taskgraph move --from=5.2 --to=7

    # Move subtask to a different parent
    taskgraph move --from=5.2 --to=7.3

    # Reorder subtasks within the same parent
    taskgraph move --from=5.2 --to=5.4

    # Move a task to a new ID position (creates placeholder if it doesn't exist)
    taskgraph move --from=5 --to=25

    # Move multiple tasks at once (must have the same number of IDs)
    taskgraph move --from=10,11,12 --to=16,17,18

    # Move a task to another tag (see Cross-Tag Task Movement)
    taskgraph move --from=5 --from-tag=backlog --to-tag=in-progress
    ```
  </Accordion>

  <Accordion title="Tag Management">
    Tags are separate, isolated task lists. All task operations work within the active tag, and most commands accept `--tag=<name>` to target a specific one.

    ```bash
    # List all tags with task counts and status
    taskgraph tags

    # List tags with detailed metadata
    taskgraph tags --show-metadata

    # Create a new empty tag, optionally with a description
    taskgraph tags add <tag-name>
    taskgraph tags add <tag-name> --description="Feature development tasks"

    # Create a tag named after the current branch
    taskgraph tags add <tag-name> --from-branch

    # Create a tag by copying tasks from another tag
    taskgraph tags add <new-tag> --copy-from=<source-tag>

    # Switch to a different tag
    taskgraph tags use <tag-name>

    # Rename or copy a tag
    taskgraph tags rename <old-name> <new-name>
    taskgraph tags copy <source-tag> <target-tag>

    # Delete a tag and all its tasks (asks for confirmation unless --yes)
    taskgraph tags remove <tag-name> --yes
    ```
  </Accordion>

  <Accordion title="Configure AI Models">
    ```bash
    # View the current model configuration
    taskgraph models

    # Set the main, research and fallback models (opus, sonnet or haiku)
    taskgraph models --set-main sonnet
    taskgraph models --set-research opus
    taskgraph models --set-fallback haiku

    # Run interactive setup
    taskgraph models --setup
    ```

    TaskGraph runs on Claude Code, so no provider API keys are needed. Configuration is stored in `.taskgraph/config.json`; runtime state such as the current tag is in `.taskgraph/state.json`. Don't edit either by hand. See [Configuration](/configuration).
  </Accordion>

  <Accordion title="Tab Completion">
    ```bash
    # Set it up for your shell (detected from $SHELL)
    taskgraph completion --install

    # Or name the shell
    taskgraph completion fish --install
    ```

    `--install` writes the script (`~/.taskgraph-completion.zsh`, `~/.taskgraph-completion.bash`, or `~/.config/fish/completions/taskgraph.fish`) and adds one line to `~/.zshrc` or `~/.bashrc` to load it. Running it again replaces the script and doesn't add the line twice. Run it again after upgrading so new commands complete.

    Tab then completes commands, flags, statuses, priorities and file paths, plus task and subtask IDs and tag names read from the project's `.taskgraph/tasks/tasks.json`. In zsh and fish each ID shows its title and status. Comma-separated lists work too: `taskgraph show 1,<Tab>` skips the IDs already listed.

    To manage your dotfiles yourself, print the script instead: `taskgraph completion zsh > ~/.taskgraph-completion.zsh`. It needs `node` on your `PATH`, which TaskGraph already requires.
  </Accordion>

  <Accordion title="Research Fresh Information">
    ```bash
    # AI-powered research with up-to-date information
    taskgraph research "What are the latest best practices for JWT authentication in Node.js?"

    # Research with task context
    taskgraph research "How to implement OAuth 2.0?" --id=15,16

    # Research with file context for code-aware suggestions
    taskgraph research "How can I optimize this API implementation?" --files=src/api.js,src/auth.js

    # Custom context and project tree
    taskgraph research "Best practices for error handling" --context="We're using Express.js" --tree

    # Different detail levels
    taskgraph research "React Query v5 migration guide" --detail=high

    # Research within a specific tag
    taskgraph research "Database optimization strategies" --tag=feature-branch

    # Save the conversation to .taskgraph/docs/research/
    taskgraph research "Database optimization techniques" --save-file

    # Save key findings to a task or subtask (recommended)
    taskgraph research "How to implement OAuth?" --save-to=15
    taskgraph research "API optimization strategies" --save-to=15.2
    ```

    The research role has web search and fetch only. It cannot read or change your files and has no shell. In the CLI you can ask follow-up questions and choose where to save findings.
  </Accordion>

  <Accordion title="Loop (Autonomous Batch Execution)">
    ```bash
    # Work through the backlog, one iteration per pending task
    taskgraph loop

    # Stop after 10 iterations
    taskgraph loop -n 10

    # Work on one task (1 iteration unless -n is given)
    taskgraph loop --id 3

    # Build a task test-first: a failing test, the code, a commit, per subtask
    taskgraph loop --id 3 --prompt tdd

    # Use a specific preset
    taskgraph loop -n 10 --prompt test-coverage
    taskgraph loop -n 10 --prompt linting
    taskgraph loop -n 10 --prompt duplication
    taskgraph loop -n 10 --prompt entropy

    # Use a custom prompt file
    taskgraph loop -n 10 --prompt ./my-workflow.md

    # Filter to tasks with a specific tag
    taskgraph loop -n 10 --tag backend

    # Custom progress file location
    taskgraph loop -n 10 --progress-file ./my-progress.txt
    ```

    **Built-in presets:**
    - `default` - Complete tasks from TaskGraph backlog one at a time
    - `test-coverage` - Write meaningful tests for untested user-facing behavior
    - `linting` - Fix lint and type errors incrementally
    - `duplication` - Refactor duplicated code into shared utilities
    - `entropy` - Clean up code smells (long functions, deep nesting, etc.)
    - `tdd` - Complete tasks test-first: RED, GREEN, COMMIT for each subtask

    Each iteration spawns a fresh Claude Code session, avoiding context fatigue. See [Loop Command](/capabilities/loop) for full documentation.
  </Accordion>
