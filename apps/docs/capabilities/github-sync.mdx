TaskGraph can mirror your tasks as GitHub Issues. Pushing is one way: TaskGraph writes the issues. Pulling is optional and reads status only: whether an issue was closed, reopened or relabelled. Importing goes the other way once: it turns issues you already have into tasks. It runs through the [`gh` CLI](https://cli.github.com), so there is no token to configure.

## Requirements

- `gh` installed and signed in (`gh auth status` should succeed)
- A project whose git remote points at the GitHub repository you want to write to, or an explicit `--repo owner/name`

Run `taskgraph github status` to check both.

## CLI

```bash
taskgraph github status                 # gh available? which repo? how many tasks are linked?
taskgraph github push --dry-run         # show the plan, write nothing
taskgraph github push                   # show the plan, ask, then write
taskgraph github push --all-tags -y     # every tag, no confirmation
taskgraph github push --id 1,2          # only top-level tasks 1 and 2
taskgraph github pull --dry-run         # show which task statuses would change
taskgraph github pull                   # show the plan, ask, then update the tasks
taskgraph github import --dry-run       # list the open issues that would become tasks
taskgraph github import                 # add a linked task for each open issue
taskgraph github unlink 3               # forget the issue task 3 is linked to
```

`push` works on the active tag unless you pass `--tag <name>` or `--all-tags`. Without `--yes` it prints the plan and asks before writing, and it refuses to write at all when it cannot ask (piped output or `--json`). Other options:

| Option | Effect |
|--------|--------|
| `--repo <owner/name>` | Write to this repository instead of the detected one |
| `--include-details` | Add the task `details` and `testStrategy` fields to issue bodies (left out by default) |
| `--close-orphans` | Close open issues whose task no longer exists |
| `--json` | Machine-readable output |

## Pulling status

`taskgraph github pull` reads the issues once and updates task statuses. It never writes to GitHub. It takes the same `--tag`, `--all-tags`, `--id`, `--repo`, `--dry-run`, `--yes` and `--json` options as `push`, and it asks before changing a status unless you pass `--yes`.

| On GitHub | Task status |
|-----------|-------------|
| Closed (as completed) | `done` |
| Closed as not planned | `cancelled` |
| Open with a `taskgraph:status/<x>` label | `<x>` |
| Open with no status label (it was reopened) | `pending` |

For each linked task, pull compares three statuses: the one at the last push or pull, the task's status now, and the issue's status.

- **Only the issue changed:** the task takes the issue's status.
- **Only the task changed:** nothing happens. A push sends it to GitHub.
- **Both changed to the same status:** pull records them as in sync.
- **Both changed to different statuses:** this is a conflict. The task keeps its local status and is listed in the plan. Run `taskgraph github push` to overwrite GitHub with it.

Tasks that were never pushed or imported, or whose issue is gone, are skipped. Pull reads issues with the `taskgraph` label; when a linked issue lacks it (an imported one), pull reads every issue in the repository instead.

## Assignees

A task's assignee is a GitHub login. Set it with `add-task --assignee` or `update <id> --assignee`, and `next --claim` sets it to your login when nobody has the task. `next --claim` prints who has the task by that login (`assigned to alice`); `--json` keeps the raw `claimedBy`. `taskgraph list --mine` shows the tasks assigned to you, and tasks with a subtask assigned to you, or says `Nothing assigned to alice` when there are none.

Assignees sync both ways. Like status, each side is compared with the assignee at the last push or pull:

- **Push** adds the task's assignee to its issue when it changed locally, then removes the one it last synced. Anyone else assigned on GitHub stays. Logins compare case-insensitively, so `Alice` in a hand-edited `tasks.json` is `alice` on GitHub.
- **Pull** gives the task the issue's assignee when it changed on GitHub and not locally, and asks first unless you pass `--yes`. When both changed, the task keeps its own and the plan lists GitHub's. An issue with several assignees keeps the task's one if it is among them, otherwise the first.
- **Import** gives each task the issue's first assignee, unless a task it links already has one. Push never writes to an imported issue, so a local change to its assignee stays local.

GitHub only accepts collaborators on the repository as assignees. When it refuses one, push stops and says which login to fix. When a new issue's assignee is dropped without an error (as GitHub does without push access to the repository), the task keeps its own. When moving an issue from its synced assignee to another doesn't take, push stops with the same hint and leaves the old assignee on the issue.

## Importing existing issues

`taskgraph github import` reads the repository's open issues and adds a task for each one that no task is linked to yet. It writes only to your tasks, never to GitHub.

- Each new task is titled `<issue title> (#<n>)`, with the issue's link and body in its details, and goes in the active tag (or `--tag <name>`).
- A task in that tag that isn't linked and whose title already ends in `(#<n>)` is linked to issue `#<n>` instead of getting a duplicate. This covers tasks you added by hand.
- Issues that are already linked, and issues written by `push`, are skipped, so running `import` again adds nothing.
- `--label <name>` imports only issues with that label. `--dry-run`, `--repo` and `--json` work as for `push`.

An imported issue stays yours: `push` never changes its title, body, labels or state. `pull` reads only whether it is open or closed. Closing the issue makes the task `done` (`cancelled` when closed as not planned), whatever its status was, and reopening it makes the task `pending` again. While the issue is open, the task's status is yours to change. Status labels on an imported issue are ignored.

```bash
taskgraph github import
# ...close issue #41 on GitHub...
taskgraph github pull -y   # the task for #41 is now done
```

## MCP tools

There is no MCP tool for pull or import, because it changes your local tasks. Use the CLI. Both tools below are in the `all` tier. Set `TASKGRAPH_TOOLS` to `all` (see [MCP Tools](/capabilities/mcp)) to load them. `all` gives the MCP host full project control. Prefer `core` or `standard` unless you need these tools.

### `github_status`

Read-only. Reports whether `gh` is usable, the repository that would be used, and the counts of linked and unlinked tasks.

| Parameter | Description |
|-----------|-------------|
| `projectRoot` | Absolute path to the project |
| `repo` | Optional `owner/name` to check instead of the detected repository |

### `github_push`

Creates, updates and closes issues. **It is a preview unless you pass `dryRun: false`**, so an agent that calls it without thinking cannot write to your repository. The intended flow is to call it once, read the plan, then call it again with `dryRun: false`.

| Parameter | Description |
|-----------|-------------|
| `projectRoot` | Absolute path to the project |
| `dryRun` | Defaults to `true`. Pass `false` to write |
| `tag` | Tag to push. Defaults to the active tag |
| `allTags` | Push every tag. Cannot be combined with `tag` |
| `id` | Comma-separated top-level task IDs to push |
| `repo` | Optional `owner/name` |
| `includeDetails` | Include `details` and `testStrategy` in bodies |
| `closeOrphans` | Close open issues whose task is gone |

The result has the plan (one step per task: `create`, `update`, `skip` or `close`, with a reason), the counts, and any orphan issues.

## What an issue looks like

- **Title:** `[<id>] <task title>`
- **Body:** a hidden marker on the first line, the description, `Blocked by #N` lines for dependencies that already have issues, and a `### Subtasks` checklist. Subtasks are part of the parent's issue, not separate issues.
- **Labels:** `taskgraph`, `taskgraph:priority/<priority>`, `taskgraph:status/<status>` while the task is open, and `taskgraph:tag/<tag>`. TaskGraph creates missing labels.
- **State:** `done` closes the issue as completed, `cancelled` closes it as not planned, anything else is open.

An unchanged task is skipped, so running `push` again is cheap and safe.

## How tasks stay linked

After the first push, each task stores its issue in its `metadata.github` field. If that is lost, the next push finds the issue again through the hidden marker on the first line of its body and relinks it, so a task is not duplicated. It relinks only issues opened by the GitHub account `gh` is signed in as; for an issue opened by another account, or when GitHub won't say which account it is (such as with the `GITHUB_TOKEN` of a GitHub Actions run), push creates a new issue instead. If the account lookup fails any other way, such as a timeout, push stops rather than risk duplicating issues; run it again.

`unlink` removes the stored link and leaves the issue alone. The marker is still in the issue body, so the next push relinks it. Remove the marker from the issue if you want the task to get a new one.

## Limits

- **Content is one way.** Only status and the assignee are read back, by `pull`, and an issue's body is read once, by `import`. Edits to an issue's title, body or subtask checkboxes are not, and the next push of a changed task overwrites them along with the labels and state.
- **Orphans are reported, not closed,** unless you pass `--close-orphans` or `closeOrphans: true`.
- **`--id` and `id` match top-level tasks.** Subtasks follow their parent.
- **Each `gh` call gets 60 seconds.** One that takes longer, for example on a stalled network or a credential prompt nobody can answer, is stopped and the command fails with a non-zero exit. A push keeps the links it saved before that, and the next push carries on from there.
