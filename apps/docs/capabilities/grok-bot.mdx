A Grok Bot connector for TaskGraph is the MCP server in `apps/mcp`, started as a stdio process. The published command is the `taskgraph-ai` bin. `npx -y taskgraph-ai` runs `dist/mcp-server.js` and speaks MCP on stdin and stdout. The same file is the `taskgraph-mcp` bin.

This page describes that process as a command, its arguments, and an environment. It does not describe Grok Bot screens or click-paths. Those were not verified. Put the object below into whatever form your bot uses for a local stdio MCP server.

## Config sample

The ready-made sample is `apps/docs/samples/grok-bot-connector.json`:

```json
{
  "command": "npx",
  "args": ["-y", "taskgraph-ai@<version>"],
  "env": {
    "TASKGRAPH_TOOLS": "core"
  }
}
```

Replace `<version>` with the version `taskgraph --version` prints, so the connector runs the release you installed. The same fields on the shell:

```bash
TASKGRAPH_TOOLS=core npx -y taskgraph-ai@<version>
```

`core` loads seven tools: `get_tasks`, `next_task`, `get_task`, `set_task_status`, `add_note`, `parse_prd`, and `expand_task`. For the daily loop, `next_task` is `taskgraph next`, `get_task` is `taskgraph show`, and `set_task_status` is `taskgraph set-status`. Each of those tool calls takes `projectRoot`, the absolute path of the project.

<Warning>
Keep `TASKGRAPH_TOOLS` at `core` for this connector. `all` registers every tool and gives the MCP host full project control. Prefer `core` or `standard`. See [MCP tools](/capabilities/mcp).
</Warning>

## Where `TASKGRAPH_TOOLS` is set

Set `TASKGRAPH_TOOLS` in the connector `env` above, or in the shell that starts the server. The server reads it from its process environment when it starts (`getToolsConfiguration` in `apps/mcp/src/tools/tool-registry.ts`). Unset, it loads `core`. The sample sets `core` so the connector states the tier.

A project's `.env` is not a source for `TASKGRAPH_TOOLS`. [GHSA-gprw-26cx-5f4r](https://github.com/stephennmiller/taskgraph-ai/security/advisories/GHSA-gprw-26cx-5f4r) passed a whole project `.env` into the Claude Code child process. A 0.61.10 allowlist was meant to stop that. [GHSA-8m93-x6f3-3mfv](https://github.com/stephennmiller/taskgraph-ai/security/advisories/GHSA-8m93-x6f3-3mfv) found the CLI and the MCP server still copied the file into `process.env`, so the allowlist never held. The effective fix for both is 0.62.14. TaskGraph does not load a project `.env` into `process.env`, and it does not pass that file's keys to Claude Code. It still reads the file, per project, only for `TASKGRAPH_TAG`, `TASKGRAPH_RESPONSE_LANGUAGE`, `TASKGRAPH_MODEL_MAIN`, `TASKGRAPH_MODEL_RESEARCH`, `TASKGRAPH_MODEL_FALLBACK`, and `TASKGRAPH_ENABLE_CODEBASE_ANALYSIS`. `TASKGRAPH_TOOLS` is not in that list. A cloned repository whose `.env` says `TASKGRAPH_TOOLS=all` leaves the server on `core`. See [Environment variables](/configuration#environment-variables).

### A project `.env` left the tier at `core`

Same directory, `.env` still `TASKGRAPH_TOOLS=all`. A second stdio client, `/tmp/tg-env-tier-check.mjs`, spawned `node /agent/repos/taskgraph-ai/dist/mcp-server.js` with that directory as the working directory. It copied the shell environment, deleted `TASKGRAPH_TOOLS` and `TASKGRAPH_PROJECT_ROOT`, set `TASKGRAPH_SKIP_AUTO_UPDATE=1` and `NO_COLOR=1`, and if `PROOF_TIER` was set wrote that value back to `TASKGRAPH_TOOLS`. It then sent `initialize` and `tools/list`.

```bash
export PROOF_ROOT=/agent/repos/taskgraph-ai
export PROOF_PROJECT=/tmp/tg-grok-proof-eUp8
env -u PROOF_TIER node /tmp/tg-env-tier-check.mjs
PROOF_TIER=core node /tmp/tg-env-tier-check.mjs
```

The client script from that check:

```js
import { spawn } from 'node:child_process';
import { createInterface } from 'node:readline';

const root = process.env.PROOF_ROOT;
const project = process.env.PROOF_PROJECT;
const env = { ...process.env };
delete env.TASKGRAPH_TOOLS;
delete env.TASKGRAPH_PROJECT_ROOT;
if (process.env.PROOF_TIER) env.TASKGRAPH_TOOLS = process.env.PROOF_TIER;
env.TASKGRAPH_SKIP_AUTO_UPDATE = '1';
env.NO_COLOR = '1';

const child = spawn(process.execPath, [`${root}/dist/mcp-server.js`], {
	cwd: project,
	env,
	stdio: ['pipe', 'pipe', 'pipe']
});
let stderr = '';
child.stderr.on('data', (d) => {
	stderr += d;
});
const pending = new Map();
createInterface({ input: child.stdout }).on('line', (line) => {
	const message = JSON.parse(line);
	if (message.id !== undefined && (message.result || message.error)) {
		pending.get(message.id)?.(message);
	}
});
let nextId = 1;
const request = (method, params) =>
	new Promise((resolve, reject) => {
		const id = nextId++;
		const timer = setTimeout(
			() => reject(new Error(`${method} timed out`)),
			20000
		);
		pending.set(id, (message) => {
			clearTimeout(timer);
			resolve(message);
		});
		child.stdin.write(
			`${JSON.stringify({ jsonrpc: '2.0', id, method, params })}\n`
		);
	});

const init = await request('initialize', {
	protocolVersion: '2024-11-05',
	capabilities: {},
	clientInfo: { name: 'grok-proof', version: '1' }
});
child.stdin.write(
	`${JSON.stringify({ jsonrpc: '2.0', method: 'notifications/initialized' })}\n`
);
const list = await request('tools/list', {});
const names = (list.result?.tools ?? []).map((tool) => tool.name).sort();
console.log('initialize_ok', !init.error);
console.log('tool_count', names.length);
console.log('tools', names.join(', '));
console.log('----- server stderr -----');
process.stdout.write(stderr);
child.stdin.end();
setTimeout(() => {
	child.kill();
	process.exit(0);
}, 300);
```

## What this check did not verify

- A Grok Bot UI, the names of its connector fields, and a live Grok Bot session. The clients were the stdio smoke script and the script above.
- `npx -y taskgraph-ai@0.63.3` as the server process. That version was not on the npm registry during the check (the registry's current version was 0.63.2). The server was the built `dist/mcp-server.js` from this checkout.
- Any tool that calls Claude Code. `parse_prd` and `expand_task` were registered and were not called. AI paths stay unverified until Stephen signs in to Claude Code.
- `next_task` with `claim: true`. The status change was `set_task_status` to `in-progress`.
