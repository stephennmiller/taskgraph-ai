## Initialize a Project

```bash
# Initialize a new project with TaskGraph structure
taskgraph init

# Import a Task Master project (.taskmaster/) into .taskgraph/
taskgraph init --from-taskmaster

# Skip the Claude Code integration (CLAUDE.md import)
taskgraph init --no-claude

# Also register the MCP server in the project's .mcp.json
taskgraph init --mcp

# Only set up Git to merge tasks.json and archive.json by task
# (existing projects; once per clone, and again after upgrading)
taskgraph init --merge-driver
```

`init` sets up the Claude Code integration by default: it copies TaskGraph's agent guide to `.taskgraph/CLAUDE.md` and imports it from your `CLAUDE.md`. `--no-claude` skips it. Slash commands and session hooks come from the plugin.

`init` writes no `.mcp.json` unless you pass `--mcp`, because the CLI and the plugin need no MCP server. `--mcp` needs the Claude Code integration, so it can't be combined with `--no-claude`. The server it adds runs `npx -y taskgraph-ai@<version>`, pinned to the CLI you ran, so a committed `.mcp.json` doesn't pick up whatever npm tags `latest`. Run `taskgraph init --mcp` again after an upgrade to move the pin; a dist-tag (`@next`), range or local path you wrote yourself is left as it is. `--rules claude` still works; `claude` is the only rule profile.

Inside a Git repository, `init` also sets up the [tasks.json merge driver](/capabilities/merge-driver), so two branches that both add or archive tasks merge without an ID clash.

`init` asks one question: whether to store tasks in Git (Yes by default, or what an earlier `init` chose). `--git-tasks`, `--no-git-tasks` or `--yes` answer it. The answer is kept in `.gitignore` as a `.taskgraph/tasks/` line under `# Task files`, commented out when tasks are stored in Git. Besides that section, `init` adds only `.taskgraph/state.json` and `.taskgraph/config.local.json` to a `.gitignore` you already have. A `.gitignore` it creates also gets a starter list: `node_modules/`, logs, `.env`, and editor and OS files. A `tasks/` or `tasks.json` line of your own stays as it is, and the unanchored `tasks.json` and `tasks/` pair an earlier `init` wrote under that header is replaced by the one anchored line. When that pair was not commented out, a `tasks/` folder or `tasks.json` elsewhere in the repo is no longer ignored afterwards, and `init` says so. Everything else takes its default: the default models (change them with `taskgraph models --setup`), English for AI responses (`taskgraph lang`), and a new Git repository if the folder isn't in one (`--no-git` skips it).

`init` changes your shell startup file only with `--aliases`, which adds `alias tm='taskgraph'` to `~/.zshrc` or `~/.bashrc`.

Without a terminal (scripts, CI, agents), `init` asks nothing: it stops with an error and exits 1 unless `--yes`, `--git-tasks`/`--no-git-tasks` (or `--name` with `--description`) answers the question. Ctrl-C at the question exits 130 and changes nothing.

## From a PRD to built tasks

```bash
# Set up the project if needed, plan the PRD into tasks, then run loop
taskgraph go docs/prd.md

# Without a terminal, or to skip the question: let loop turn Claude's
# permission prompts off
taskgraph go docs/prd.md --trust

# Or run loop in Docker sandbox mode
taskgraph go docs/prd.md --sandbox
```

`go` runs `init --yes` when the folder isn't a TaskGraph project yet, then
`parse-prd <file> --append` (new sections become tasks; tasks you already have
stay), then [`loop`](/capabilities/loop) with the default preset. `init` and
`parse-prd` print their result without a next step, since `go` runs the next
step itself. The first step that fails stops the rest, and `go` exits with its
code. Stopping `go` (Ctrl-C, `kill`, closing the terminal) stops the step that
is running too.

`loop` runs Claude Code with permission prompts off, so `go` asks you to
allow that before its first step, unless you passed `--trust` or `--sandbox`.
Answering no, or Ctrl-C, stops it before anything is set up or planned.
Without a terminal it stops there with an error instead of asking. A yes
covers the tasks this run plans from the PRD, and is remembered as
[`loop` remembers it](/capabilities/loop-trust).

An approval you gave earlier doesn't answer for tasks that aren't planned
yet: `go` asks whenever it is going to plan (the folder isn't a project yet,
or the PRD has sections with no tasks, or it can't tell). When you run `go`
again and every section already has its tasks, nothing new is planned and an
approval the project still has stands, as it does for `loop`.

When you run `go` again on a project with work done or under way, it prints
one line saying what it is resuming before `loop` starts:

```
Resuming: 3 done, task 4 in progress, 5 pending
```

A first run, with every task still pending, prints no such line.

## Check the Setup

```bash
# Check Node, Claude Code and its sign-in, the project, its data files and
# tasks, the plugin and the MCP server
taskgraph doctor

# Also repair the task problems that have one safe answer
taskgraph doctor --fix

# The same checks as JSON
taskgraph doctor --json
```

Each check gets one line: `✓` when it passed, `✗` with the fix under it when it failed, and `–` for the plugin when it isn't installed and the MCP server when it isn't set up, since both are optional. Checks that need Claude Code are left out when it isn't installed, and the project's own checks outside a project.

`doctor` exits 0 when no check failed and 1 when one did. With `--fix` the exit code is for what is left after the repair. It works outside a project.

```
✓ Node            22.22.0
✓ Claude Code     2.1.309
✓ Claude sign-in  signed in
✓ Project         .
✓ Data files      3 files read
✓ Tasks           42 in 2 tags
– Plugin          optional; not installed
  In Claude Code, run /plugin marketplace add stephennmiller/taskgraph-ai
  then /plugin install taskgraph@taskgraph
  and /plugin install taskgraph-hooks@taskgraph for its hooks
– MCP server      optional; add it with taskgraph init --mcp
```

The CLI works without the plugin, so a missing one doesn't fail. The plugin check fails when the plugin is installed but disabled, or when this CLI is older than the installed plugin needs. The MCP check looks in the project's `.mcp.json` and in Claude Code's own config (`claude mcp add`), without starting the server.

### Data files and tasks

In a project, `doctor` parses `.taskgraph/config.json`, `config.local.json`, `state.json`, `tasks/tasks.json` and `tasks/archive.json`. A missing file is fine, and so is an empty `config.local.json`. One that is empty or isn't valid JSON fails the check, with the file and, when it can be told, the line. A git conflict marker is always found:

```
✗ Data files      1 can't be read
  .taskgraph/config.json has a git conflict marker on line 3
    Resolve the conflict in the file, then run taskgraph doctor again
```

It then checks every tag of `tasks.json`, without changing it, for:

- a status or priority that isn't a known one, on a task or subtask
- an ID that isn't a whole number from 1, and two tasks in a tag (or two subtasks of a task) with the same ID
- what [`fix-dependencies --check`](/capabilities/cli-updating-commands#managing-task-dependencies) reports: a dependency or link to a task that doesn't exist, a task that depends on itself, a dependency loop

```
✗ Tasks           2 problems in .taskgraph/tasks/tasks.json
  Task 2 has status "finished"
    Run taskgraph set-status --id=2 --status=pending --tag=master, then set
    the status it should have
  Task 6 depends on non-existent task 99
  Run taskgraph doctor --fix to repair 1 of them
```

`doctor --fix` repairs the problems with one safe answer, in every tag, and lists each change. Those are the dependency problems, as `fix-dependencies` repairs them: it drops the ones on missing tasks, on the task itself and repeats, and breaks loops made only of subtasks.

```
✓ Repaired 1 problem in .taskgraph/tasks/tasks.json
  Task 6 no longer depends on 99, which doesn't exist
```

Everything else needs a decision, so it stays reported with its fix: an unknown status (`set-status` on that task to `pending`, then to the status it should have), an unknown priority or a bad or duplicate ID (edit the file), a loop between tasks. Until an unknown status or priority on a task is fixed, `list`, `next` and `show` stop with the task and `Run taskgraph doctor to see how to fix it`. `--fix` writes nothing while one of the five files can't be read, and never rewrites a file it couldn't parse.

A parent's status is not checked against its subtasks. `set-status` may mark a parent `done` over open subtasks, or set it back over finished ones, and every command keeps that status until a subtask changes, so `doctor` has nothing to tell a stale status from a chosen one and leaves it alone.

Commands can no longer save such a value: a write that would add an unknown status or priority, or a bad or duplicate ID, is refused with the task and the field. A value already in the file may stay until you fix it.

### JSON

The JSON has `ok`, `cliVersion` and `checks`, each with `name` (`node`, `claude`, `signed-in`, `project`, `data-files`, `tasks`, `plugin`, `mcp`), `status` (`pass`, `fail`, `skip`) and, when they apply, `detail`, `problem` and `required`. A failed `data-files` or `tasks` check has `findings`: each with `kind` (`unreadable-file`, `unknown-status`, `unknown-priority`, `bad-id`, `duplicate-id`, `dependency`, `unchecked`), `file`, `message`, `fixable` (whether `--fix` repairs it) and, when they apply, `line`, `tag`, `taskId` and `fix`. With `--fix`, the `tasks` check has `repaired` (each with `tag`, `taskId` and `message`) when it changed something, or `repairError` when it couldn't.

## Install the latest version

```bash
taskgraph upgrade
```

This installs the newest `taskgraph-ai` from npm. Other commands only tell you when a newer version is out. See [Staying up to date](/getting-started/installation#staying-up-to-date).

`upgrade` installs nothing, and exits 1, when `loop` or `loop --parallel` started the process.

## Tag Management

Tags are separate, isolated task lists. All task operations work within the active tag, and most commands accept `--tag=<name>` to target a specific one.

```bash
# List all tags with task counts and status
taskgraph tags

# List tags with detailed metadata
taskgraph tags --show-metadata

# Create a new empty tag, optionally with a description
taskgraph tags add <tag-name>
taskgraph tags add <tag-name> --description="Feature development tasks"

# Create a tag named after the current branch
taskgraph tags add <tag-name> --from-branch

# Create a tag by copying tasks from another tag
taskgraph tags add <new-tag> --copy-from=<source-tag>

# Switch to a different tag
taskgraph tags use <tag-name>

# Rename or copy a tag
taskgraph tags rename <old-name> <new-name>
taskgraph tags copy <source-tag> <target-tag>

# Delete a tag and all its tasks (asks for confirmation unless --yes)
taskgraph tags remove <tag-name> --yes
```

A copy (`tags copy` or `tags add --copy-from`) leaves out each task's GitHub link and claim, so pushing the copy creates its own issues. A removed or renamed tag's name keeps its highest task ID, so a new tag with that name numbers its tasks above it, and the tag's complexity report is deleted or renamed with it. A copy or rename onto a removed or renamed tag's name is refused when it would bring back one of that tag's IDs; renaming a tag back to its old name is allowed. To put tasks under such a name anyway, run `taskgraph tags add <name>` and then `taskgraph move --from <ids> --from-tag <tag> --to-tag <name>`: the move gives them new IDs above the retired ones (copy the tag to a spare name first to keep the originals).

## Configure AI Models

```bash
# View the current model configuration
taskgraph models

# Set the main, research and fallback models (opus, sonnet or haiku)
taskgraph models --set-main sonnet
taskgraph models --set-research opus
taskgraph models --set-fallback haiku

# Run interactive setup
taskgraph models --setup
```

TaskGraph runs on Claude Code, so no provider API keys are needed. Configuration is stored in `.taskgraph/config.json`; runtime state such as the current tag is in `.taskgraph/state.json`. Don't edit either by hand. See [Configuration](/configuration).

## Tab Completion

```bash
# Set it up for your shell (detected from $SHELL)
taskgraph completion --install

# Or name the shell
taskgraph completion fish --install
```

`--install` writes the script (`~/.taskgraph-completion.zsh`, `~/.taskgraph-completion.bash`, or `~/.config/fish/completions/taskgraph.fish`) and adds one line to `~/.zshrc` or `~/.bashrc` to load it. Running it again replaces the script and doesn't add the line twice. Run it again after upgrading so new commands complete.

Tab then completes commands, flags, statuses, priorities and file paths, plus task and subtask IDs and tag names read from the project's `.taskgraph/tasks/tasks.json`. In zsh and fish each ID shows its title and status. Comma-separated lists work too: `taskgraph show 1,<Tab>` skips the IDs already listed.

To manage your dotfiles yourself, print the script instead: `taskgraph completion zsh > ~/.taskgraph-completion.zsh`. It needs `node` on your `PATH`, which TaskGraph already requires.

## Loop (Autonomous Batch Execution)

```bash
# Work through the backlog, one iteration per pending or in-progress task
taskgraph loop

# Stop after 10 iterations
taskgraph loop -n 10

# Work on one task (1 iteration unless -n is given)
taskgraph loop --id 3

# Build a task test-first: a failing test, the code, a commit, per subtask
taskgraph loop --id 3 --prompt tdd

# Use a specific preset
taskgraph loop -n 10 --prompt test-coverage
taskgraph loop -n 10 --prompt linting
taskgraph loop -n 10 --prompt duplication
taskgraph loop -n 10 --prompt entropy

# Use a custom prompt file
taskgraph loop -n 10 --prompt ./my-workflow.md

# Filter to tasks with a specific tag
taskgraph loop -n 10 --tag backend

# Custom progress file location
taskgraph loop -n 10 --progress-file ./my-progress.txt
```

**Built-in presets:**
- `default` - Complete tasks from TaskGraph backlog one at a time
- `test-coverage` - Write meaningful tests for untested user-facing behavior
- `linting` - Fix lint and type errors incrementally
- `duplication` - Refactor duplicated code into shared utilities
- `entropy` - Clean up code smells (long functions, deep nesting, etc.)
- `tdd` - Complete tasks test-first: RED, GREEN, COMMIT for each subtask

Each iteration spawns a fresh Claude Code session, avoiding context fatigue. See [Loop Command](/capabilities/loop) for full documentation.
