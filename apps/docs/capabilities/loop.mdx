# Loop Command

The `loop` command runs Claude Code in autonomous loops, spawning fresh agent sessions for each iteration. This approach, known as the "Ralph Wiggum pattern" (credited to Jeffrey Huntley, popularized by Matt Pocock), maintains context quality by avoiding long-running sessions that accumulate context fatigue.

## Overview

Instead of a single long-running agent session that degrades over time, the loop command:

1. **Spawns fresh sessions** - Each iteration starts with a clean context
2. **Uses preset prompts** - Built-in or custom prompts guide each iteration
3. **Tracks progress** - A progress file persists notes across sessions
4. **Detects completion** - Special markers signal when work is done or blocked

This pattern is ideal for batch operations like clearing task backlogs, improving test coverage, or fixing lint errors across a codebase.

## Basic Usage

Work through the backlog with the default task-completion preset, one iteration per pending task:

```bash
taskgraph loop
```

Cap the run at 10 iterations:

```bash
taskgraph loop -n 10
```

Run 5 iterations with the test-coverage preset:

```bash
taskgraph loop -n 5 --prompt test-coverage
```

Run iterations with a custom prompt file:

```bash
taskgraph loop -n 10 --prompt ./my-custom-prompt.md
```

Filter to specific task tag:

```bash
taskgraph loop -n 10 --tag backend
```

Work on one task (or subtask) instead of the one `taskgraph next` picks. It runs one iteration unless you pass `-n`:

```bash
taskgraph loop --id 3
taskgraph loop --id 3.2 --prompt tdd
```

`--id` works with the `default` and `tdd` presets and with custom prompt files. The other presets pick their own work, so `loop` refuses `--id` with them. A task ID that doesn't exist fails before Claude Code starts.

Watch Claude work as it goes, instead of seeing each iteration's output when it ends:

```bash
taskgraph loop -n 5 --verbose
```

### Cost, caps and models

Each iteration's status line shows what it cost, how many turns it took and the model and effort it ran at. `--max-turns` and `--max-budget-usd` cap a run, a task's complexity score picks its model and effort and `--reuse-session` resumes the last iteration's Claude Code session for the next task. See [Loop cost and models](/capabilities/loop-cost).

### Permission prompts

Each iteration runs `claude -p` with permission prompts off (`--dangerously-skip-permissions`), so Claude can read, edit and run anything in the project without asking. The first run in a project asks you to allow that and remembers your answer in `~/.taskgraph/loop-trusted.json`. It asks again when the task text changed since you approved it: after `parse-prd` or `github import` adds tasks, or after a command saves text from the research model (with `--research`, or when it answered because the main and fallback models failed), since that text came from someone other than you or from the web, and after the tasks file changed some other way, such as checking out a branch with different tasks or editing a task. Status changes and checked-off criteria don't count, and neither do the changes an approved run makes itself, except that saving research-model output during a run still withdraws the approval. Approvals saved before this check existed are asked for once more. `show`, `next` and `prime` print task text between `<task-data>` and `</task-data>`, and each prompt tells Claude that text describes the work and doesn't instruct it. In a script or CI, where nothing can answer, pass `--trust`. To keep Claude off your machine, pass `--sandbox` to run each iteration in a Docker sandbox (`docker sandbox run claude`) instead; the first sandbox run asks you to sign in. Every iteration in a project uses the same sandbox, named `taskgraph-loop-<id>`, and an iteration that times out or a Ctrl-C stops it (`docker sandbox stop`). If you used `--sandbox` before the sandbox had this name, your first run after upgrading creates it and asks you to sign in once more.

## How It Works

Each loop iteration:

1. Builds a prompt from a short header (the progress file and `CLAUDE.md` as `@` references, the iteration number, the tag and any `--id` task) followed by the preset or custom prompt
2. Spawns `claude -p <prompt>` as a fresh subprocess in the project root
3. Captures output and checks for completion markers
4. Waits 5 seconds before the next iteration

The agent appends its own notes to the progress file as the prompt tells it to.

The loop stops when:
- An agent ends its reply with `<loop-complete>REASON</loop-complete>` - all work done
- An agent ends its reply with `<loop-blocked>REASON</loop-blocked>` - cannot proceed
- Maximum iterations reached
- With `--max-budget-usd`: the run has spent the amount
- Three iterations in a row fail (Claude Code exits non-zero or runs past the iteration timeout), or Claude Code isn't installed: the loop stops with status `error` and the last error
- With the `default` and `tdd` presets, or with `--id`: two iterations in a row finish without changing any task's status or making a commit. The loop stops with status `error` and names the task it is stuck on

Each iteration gets an hour. One that runs longer is stopped and counts as a failed iteration. Set `TASKGRAPH_LOOP_TIMEOUT_MS` (milliseconds) to change it; see [Loop iteration timeout](/best-practices/configuration-advanced#loop-iteration-timeout).

A marker counts only alone on the last line of the reply, so an agent that quotes one mid-sentence doesn't stop the loop. With the `default` and `tdd` presets, `<loop-complete>` also needs `taskgraph next` to find nothing: if a task is still ready, the loop warns and keeps going.

It then prints the number of iterations, the tasks completed and the final status. A task counts as completed when an iteration moved it to `done` or `review`, not when Claude Code exited without an error. A parent that moves to `done` because its last subtask did is not counted again. The exit code is 1 when the loop ended blocked or on an error, and 0 otherwise, so a script can tell a stuck loop from a finished one.

## CLI Options

| Option                   | Type   | Default                         | Description                                                                                                   |
| ------------------------ | ------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `-n, --iterations`       | number | see description                 | Maximum number of iterations to run. Without it: 1 with `--id`; the number of pending tasks and subtasks with the `default` and `tdd` presets (10 when none are pending); otherwise 10. |
| `-i, --id`               | string | -                               | Work on this task or subtask (`3`, `3.2`) instead of the next one. Runs 1 iteration unless `-n` is given. Works with the `default` and `tdd` presets and custom prompt files. |
| `-p, --prompt`           | string | `default`                       | Preset name or path to a custom prompt file. Accepts: `default`, `tdd`, `test-coverage`, `linting`, `duplication`, `entropy`, or a file path like `./my-prompt.md`. |
| `--progress-file`        | string | `.taskgraph/progress.txt`       | Path to the progress log file, attached to every iteration's prompt. A relative path is relative to the project root. |
| `-t, --tag`              | string | -                               | Filter to only work on tasks with this tag.                                                                   |
| `--project`              | string | -                               | Project root directory. Auto-detected if not provided.                                                        |
| `--sandbox`              | flag   | -                               | Run each iteration in a Docker sandbox (`docker sandbox run claude`) instead of on this machine.              |
| `--trust`                | flag   | -                               | Run Claude with permission prompts off without asking first. For scripts and CI.                              |
| `--no-output`            | flag   | -                               | Hide Claude's output, including with `--verbose`; show only each iteration's status line and the summary.     |
| `-v, --verbose`          | flag   | -                               | Show Claude's work (its messages and tool calls) as it happens.                                               |
| `--max-turns`            | number | -                               | Stop each Claude Code run after this many turns. See [Cost and caps](/capabilities/loop-cost#cost-and-caps).                          |
| `--max-budget-usd`       | number | -                               | Stop the run once it has spent this many US dollars; each iteration gets what's left. See [Cost and caps](/capabilities/loop-cost#cost-and-caps). |
| `--model`                | string | -                               | Run every iteration on this model instead of the one the task's complexity picks. See [Model and effort by complexity](/capabilities/loop-cost#model-and-effort-by-complexity). |
| `--reuse-session`        | flag   | -                               | Resume the last iteration's Claude Code session for the next task instead of starting a new one. See [Session reuse](/capabilities/loop-cost#session-reuse). |
| `--parallel`             | number | -                               | Run up to N ready tasks at once, each in its own git worktree and branch. See [Run tasks in parallel](/capabilities/loop-parallel). |
| `--container`            | flag   | -                               | With `--parallel`: run each task in its own Docker container. See [Run each task in a container](/capabilities/loop-parallel#run-each-task-in-a-container). |
| `--container-image`      | string | `docker/sandbox-templates:claude-code` | The image `--container` uses.                                                                          |

### Option Details

**`--prompt` accepts two types of values:**
- **Preset names**: Use built-in presets like `default`, `tdd`, `test-coverage`, `linting`, `duplication`, or `entropy`
- **File paths**: Provide a path to a custom prompt file (e.g., `./my-custom-loop.md`)

## Run tasks in parallel

`taskgraph loop --parallel N` runs up to N independent tasks side by side, each in its own git worktree and branch. See [Run tasks in parallel](/capabilities/loop-parallel).

## Built-in Presets

Six built-in presets cover common workflows: `default` (the TaskGraph backlog), `tdd` (the backlog, test-first), `test-coverage`, `linting`, `duplication` and `entropy`. See [Loop Presets](/capabilities/loop-presets) for what each one does.

## Custom Prompts

You can create custom prompt files for specialized workflows that aren't covered by the built-in presets.

### Specifying a Custom Prompt

Pass the file path to the `--prompt` option:

```bash
taskgraph loop -n 10 --prompt ./my-custom-loop.md
```

The path can be absolute or relative to the current directory.

### Required Structure

Custom prompts should follow this structure to work effectively with the loop system:

```markdown
# Your Loop Title

Brief description of what this loop does.

## Files Available

- @.taskgraph/tasks/tasks.json - Your task backlog
- @path/to/other/file.ts - Any other files the agent needs

## Process

1. Step one of the workflow
2. Step two of the workflow
3. ... more steps

## Important

- Complete ONLY ONE task per session
- Keep changes small and focused
- Do NOT start another task after completing one
- If work is complete, output: <loop-complete>REASON</loop-complete>
- If blocked, output: <loop-blocked>REASON</loop-blocked>
```

### File References with @ Syntax

The `@` prefix makes files available to the agent. Claude Code will read these files when processing the prompt:

```markdown
## Files Available

- @src/index.ts - Main entry point
- @package.json - Dependencies and scripts
```

Without the `@` prefix, file paths are just text. With `@`, the agent can actually read and reference the file contents.

### Completion Markers

The loop watches for two special markers in agent output:

| Marker | Purpose | Example |
| ------ | ------- | ------- |
| `<loop-complete>REASON</loop-complete>` | Signal that all work is done | `<loop-complete>ALL_TESTS_PASSING</loop-complete>` |
| `<loop-blocked>REASON</loop-blocked>` | Signal that work cannot proceed | `<loop-blocked>MISSING_ENV_VAR</loop-blocked>` |

When either marker is detected, the loop exits early. The reason text is captured in the final result.

**Example usage in a custom prompt:**

```markdown
## Important

- If all migrations are complete, output: <loop-complete>MIGRATIONS_DONE</loop-complete>
- If a migration fails with an unrecoverable error, output: <loop-blocked>MIGRATION_FAILED: describe error</loop-blocked>
```

### Best Practices

1. **Be specific**: Clearly define what "done" means for your workflow
2. **One task per iteration**: Instruct agents to complete exactly one unit of work
3. **Use the progress file**: It is attached to every prompt; tell agents to append a note to it so the next iteration sees what was done
4. **Include quality checks**: Add steps for running tests or type checks before completing
5. **Define completion criteria**: Tell agents exactly when to output `<loop-complete>`
6. **Handle edge cases**: Define when to output `<loop-blocked>` to avoid infinite loops

## Progress File

The progress file is a shared log that persists notes across loop iterations. Since each iteration spawns a fresh agent session, this file provides continuity.

### Default Location

```
.taskgraph/progress.txt
```

Override with the `--progress-file` option:

```bash
taskgraph loop -n 10 --progress-file ./my-progress.txt
```

### How It Works

1. **Start**: The loop appends a header to the file, creating it if needed. Earlier runs' notes are kept.
2. **Each iteration**: The prompt attaches the file with an `@` reference, and the agent appends notes about its work. When the iteration ends, the loop appends a line with its status, cost, turns and duration.
3. **End**: The loop appends a summary of the run, with the total cost and turns

### File Format

The loop writes the header and the summary; the lines in between are whatever the agents append:

```
# TaskGraph Loop Progress
# Started: 2026-01-09T10:30:00.000Z
# Preset: default
# Max Iterations: 10
# Tag: backend

---

Task 5.2: added the login endpoint. Learned: tokens live in src/auth/token.ts
# Iteration 1: success · $0.42 · 12 turns · 190s
Task 5.3: validated the login form input
# Iteration 2: complete · $0.31 · 9 turns · 124s

---
# Loop Complete: 2026-01-09T10:41:12.000Z
- Total iterations: 2
- Tasks completed: 2
- Final status: all_complete
- Spent: $0.73 · 21 turns
```

The `# Tag:` line appears only with `--tag`. The cost and turns are left out when Claude Code didn't report them.

### Using Progress in Custom Prompts

The loop attaches the progress file to every prompt, so a custom prompt doesn't need to reference it. Tell agents to append notes:

```markdown
## Process

...
7. Append a brief note to the progress file about what was done
```

This creates a chain of context that helps each iteration build on previous work.

## Real-World Examples

Here are practical scenarios for using the loop command in your development workflow.

### Weekend Automation

Run a loop overnight or over the weekend to clear your task backlog while you're away:

```bash
taskgraph loop -n 50 --trust && notify-send "Loop finished"
```

This runs up to 50 iterations, completing tasks one by one. `--trust` skips the permission question so nothing waits for you, and `&&` sends a desktop notification only if the loop didn't end blocked or on an error.

### Test Coverage Sprint

Push your test coverage from 60% to 80% systematically:

```bash
taskgraph loop -n 20 --prompt test-coverage
```

Each iteration identifies the most important untested user-facing behavior and writes a meaningful test. The agent prioritizes error handling, API endpoints, and CLI commands over internal utilities.

### Tech Debt Day

Dedicate a day to cleaning up lint errors across your codebase:

```bash
taskgraph loop -n 30 --prompt linting
```

The agent systematically addresses type errors first (they break builds), then security-related lint errors, then others.

### Code Review Prep

Reduce code duplication before opening a PR:

```bash
taskgraph loop -n 10 --prompt duplication
```

Each iteration finds and refactors one instance of duplicated code into a shared utility.

### Multi-Tag Workflow

Process different parts of your codebase in sequence:

```bash
# First, handle critical backend tasks
taskgraph loop -n 10 --tag backend

# Then, address frontend tasks
taskgraph loop -n 10 --tag frontend
```

### Custom Migration Script

For complex migrations, create a custom prompt and run it:

```bash
# Create custom-migration.md with your specific steps
taskgraph loop -n 20 --prompt ./custom-migration.md --progress-file ./migration-progress.txt
```

Use a separate progress file to track migration-specific notes.
